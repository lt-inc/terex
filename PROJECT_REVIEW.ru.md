# Разбор Terex — 3 октября 2026

Репозиторий: https://github.com/lt-inc/terex. Локальная копия: `F:\terex`, ветка `master`, коммит `d90bb66bd7191b8edf9a8a6645a47e33040e9039`.

**Главный вывод.** У проекта есть хорошая основа для сервиса «длинное видео → короткие ролики → модерация → публикация»: разделены управляющий backend и GPU-обработка, предусмотрены очереди, объектное хранилище, шаблоны каналов и трассировка. Сейчас главные ограничения — надежность выполнения, безопасность доступа и незавершенная публикация. Добавление новых моделей или платформ до устранения этих ограничений увеличит стоимость поддержки и число потерянных заданий.

Исходники приложения не исправлялись. Этот файл содержит результаты аудита и предлагаемый план. Изучена актуальная Go-архитектура; оставшийся Python `BE/` рассмотрен как предыдущая реализация и источник рисков миграции.

**Что уже сделано хорошо**

- `main-be` управляет данными и расписаниями; `gpu-be` выполняет тяжелую обработку. Их можно развивать и размещать независимо.
- Общие контракты вынесены в `proto`; основные зависимости сервисов представлены интерфейсами, что упрощает проверку без реального GPU.
- PostgreSQL хранит ссылки на файлы, MinIO хранит сами файлы; загрузки через подписанные URL разгружают backend.
- Нарезка highlights опирается на границы предложений и временные отметки слов; проверяется длина и пересечение клипов. Есть акустические подсказки и разделение длинного транскрипта на части.
- Есть ручное одобрение, автоматическое одобрение, шаблоны каналов, тесты отдельных алгоритмов, OpenTelemetry и панели Grafana.

**Подтвержденные недоработки, которые следует исправить**

Приоритет «срочно» означает защиту доступа либо риск потери/нежелательной отправки контента. Следующие находки подтверждены кодом; там, где выполнено локальное воспроизведение, это указано отдельно. Наличие и настройки внешней защиты production-инфраструктуры не проверялись.

1. **Срочно: в Git закоммичен похожий на настоящий OpenRouter API-ключ.** В [docker-compose.yml](F:/terex/docker-compose.yml:95) он задан как fallback: при отсутствии переменной окружения используется значение из исходников. Действительность ключа не проверялась; его значение здесь не приведено. Следует отозвать/заменить ключ у провайдера, убрать fallback, передавать секрет через окружение или secret storage, добавить проверку секретов в CI. Удаление строки из текущего файла само по себе не удалит ее из истории Git.

2. **Срочно: через регистрацию баннеров можно получить и удалить файлы авторизации аккаунтов.** API не содержит проверки пользователя и прав. Список аккаунтов раскрывает ссылки на файлы; регистрация баннера принимает произвольные `bucket/object`, а затем выдает подписанную ссылку на этот объект. Удаление такого баннера удаляет тот же объект. Это позволяет обратиться к файлу в `cookies`, если API доступен вызывающему. Доказательства: [router.go](F:/terex/main-be/internal/transport/http/router.go:28), [assets.go](F:/terex/main-be/internal/service/assets/assets.go:67), [storagegw.go](F:/terex/gpu-be/internal/service/storagegw/storagegw.go:28). Нужны авторизация API, проверка принадлежности объекта ресурсу, запрет preview для auth-файлов, отдельные права хранилища для секретов. Регистрацию загрузки лучше подтверждать серверным upload token, а не доверять произвольной ссылке клиента.

3. **Срочно: используется уязвимый Next.js 15.2.4.** Версия закреплена в [package.json](F:/terex/FE/package.json:12); проект использует App Router. Официальный бюллетень описывает критическую RCE в соответствующей ветке: [Next.js CVE-2025-66478](https://nextjs.org/blog/CVE-2025-66478). Локальный `npm audit --omit=dev` сообщает 4 проблемных пакета: 1 critical и 3 high; полный audit — 17 записей по пакетам. Это не число независимо эксплуатируемых уязвимостей. Следует обновить Next.js и зависимости до актуальных исправленных версий, повторить audit и smoke-проверки. Минимальный фикс из старого бюллетеня закрывает конкретную RCE, но не обязательно все последующие проблемы. Эксплуатация на действующем сервере не проверялась.

4. **Срочно: временный сбой или обычный restart может безвозвратно потерять задачу.** При любой ошибке обработчика общий брокер вызывает `Nack(false, false)`; очереди объявлены без DLX. При завершении GPU-процесса общий context отменяется, активные команды останавливаются и возвращают ошибку: сообщение может быть выброшено вместо повторной обработки после запуска. Аналогично теряются результаты при кратковременном сбое БД. Доказательство: [broker.go](F:/terex/proto/amqpx/broker.go:180), [gpu main.go](F:/terex/gpu-be/cmd/gpu-be/main.go:47). Нужны ограниченные повторы с задержкой, DLQ, отдельная обработка shutdown и идемпотентность стадий. Публикация сообщений также не использует publisher confirms: [broker.go](F:/terex/proto/amqpx/broker.go:108).

5. **Срочно: монитор помечает видео просмотренным до успешного создания задания.** В [monitor.go](F:/terex/main-be/internal/service/monitor/monitor.go:106) `MarkSeen` выполняется раньше `Jobs.Create`. Если создание или постановка задания не удалась, следующий проход мониторинга пропустит видео. Исправление: транзакционно связывать источник видео, создание job и запись события для отправки; outbox должен гарантировать повторную доставку после сбоя. Уникальный ключ источника защитит от дубликатов.

6. **Срочно: scheduler может навсегда оставить публикации в `sent`.** [DuePublications](F:/terex/main-be/internal/repository/postgres/clips.go:99) сначала переводит до 50 публикаций в `sent`, после чего [Tick](F:/terex/main-be/internal/service/publish/publish.go:94) отправляет их по одной. Авария между этими действиями оставляет неотправленные записи в состоянии, которое больше не выбирается. Нужны transactional outbox либо аренда задания с ограниченным сроком и восстановление зависших записей. Внешний upload должен иметь устойчивый ключ идемпотентности.

7. **Срочно: отклонение клипа и удаление подзадачи не отменяют запланированные публикации.** `Reject` меняет только approval: [publish.go](F:/terex/main-be/internal/service/publish/publish.go:70). Scheduler не проверяет актуальное одобрение. Удаление sub-job оставляет publications через `ON DELETE SET NULL`: [migration](F:/terex/main-be/migrations/001_init.sql:98). Сценарий approve → reject до времени публикации все равно приведет к dispatch; удаленная подзадача тоже может отправиться. Нужны состояние `cancelled`, атомарная отмена будущих публикаций и повторная проверка допуска перед отправкой. Сейчас отправку принимает заглушка; при реализации реального publisher проблема станет внешне видимой.

8. **Высокий: время публикации при создании задания сдвигается на 7 часов.** FE переводит дату и время в UTC, а backend повторно трактует полученные поля как UTC+7: [upload-video/page.tsx](F:/terex/FE/src/app/admin/upload-video/page.tsx:13), [jobs.go](F:/terex/main-be/internal/service/jobs/jobs.go:39). Локальное воспроизведение с настоящей TS-функцией: `03.10.2026 12:00` в Томске → FE отправляет `05:00` → backend получает `02.10.2026 22:00Z`, то есть `03.10 05:00` в Томске. Нужен единый RFC3339 timestamp с зоной при создании и редактировании; отображаемая зона должна быть явной.

9. **Высокий: независимые расписания платформ превращаются в одно.** Интерфейс задает время и шаг отдельно для YouTube/TikTok/Instagram, но [subJob](F:/terex/main-be/internal/service/jobs/jobs.go:61) объединяет аккаунты и применяет первое подходящее расписание. YouTube на 12:00 и TikTok на 18:00 будут назначены на одинаковое время. Дополнительно подсказка UI предлагает шаг `1d`, а [parser](F:/terex/main-be/internal/service/jobs/jobs.go:52) использует `Atoi` и молча получает ноль: все клипы могут назначиться одновременно. Следует хранить расписание по получателю/платформе и валидировать единицу шага; простой контракт — целое число минут.

10. **Высокий: смешанные варианты с баннером и без баннера могут упасть на рендере.** В [renderer.go](F:/terex/gpu-be/internal/service/renderer/renderer.go:136) безусловно удаляется `base`. Для варианта без баннера `base == cur`, поэтому следующий вариант теряет исходник. Локальный тест с fake Store/Media подтвердил: порядок `[banner, без баннера]` проходит, `[без баннера, banner]` падает с отсутствующим `src.mp4`. Временный тест удален; исходная реализация не исправлялась. Следует удалять только самостоятельный файл варианта и сохранять общий исходник до окончания цикла. Добавить постоянную проверку обоих порядков.

11. **Высокий при доступе недоверенных пользователей: URL канала допускает запросы к внутренним HTTP-сервисам.** [ResolveChannel](F:/terex/main-be/internal/repository/youtube/feed.go:33) принимает произвольный host и делает GET; redirects также не ограничены. Подтверждена возможность инициировать запрос, а не произвольное чтение ответа через API. Нужны разрешенные YouTube hosts, проверка redirect destinations и запрет private адресов; сырой channel ID можно обрабатывать без сетевого запроса.

12. **Средний: API-ошибки интерфейс показывает как успех.** [submitJobs](F:/terex/FE/src/lib/api.ts:137) не проверяет `r.ok`; создание аккаунтов и удаление аккаунтов/баннеров/фонов имеют аналогичные пропуски. Локальный probe реального `api.ts` с ответом HTTP 500 подтвердил успешное завершение этих функций. Пользователь видит «queued/created», либо запись исчезает до обновления страницы, хотя сервер не выполнил действие. Нужен общий API client с проверкой статуса, сообщением из ответа и результатом каждой карточки при пакетной отправке.

13. **Средний: изменения подзадачи не пересчитывают будущие публикации.** [UpdateSubJob](F:/terex/main-be/internal/repository/postgres/jobs.go:177) обновляет только sub_jobs; уже созданные publications сохраняют прежние время и аккаунты. При вызове API после scheduling сохранение проходит, а фактический план остается старым. Часть редактирования заблокирована UI для активных задач, но API такого ограничения не обеспечивает. Следует пересчитывать неотправленные публикации транзакционно или явно отклонять изменения, которые уже не могут примениться.

14. **Высокий для перехода с Python-версии: отсутствует миграция существующей БД.** Старая [Alembic schema](F:/terex/BE/alembic/versions/001_schema.py:17) создает `jobs/accounts/banners` и другие таблицы. Новая [Go migration](F:/terex/main-be/migrations/001_init.sql:2) начинает с `CREATE TABLE accounts`; [startup](F:/terex/main-be/internal/repository/postgres/store.go:51) автоматически запускает goose. Подключение новой версии к старой БД без отдельной подготовки столкнется с уже существующими таблицами. Это условный сценарий обновления, состояние production-БД не известно. Нужны явная миграция/импорт старых данных, проверка на копии БД и описанный rollback; нельзя просто менять имя образа и считать переход завершенным.

**Функциональные пробелы и дополнительные несоответствия**

- **Реальная публикация не реализована.** [publisher.Stub](F:/terex/gpu-be/internal/service/publisher/publisher.go:17) возвращает фиктивный upload ID, ничего не размещая. Это явно документированная заглушка. Для завершения полного цикла нужны adapters платформ, управление авторизацией, повторные попытки, получение реального результата и reconciliation. Текущий [PublishClip](F:/terex/proto/msg/msg.go:69) передает идентификаторы и время; для настоящего uploader потребуется дополнить контракт ссылкой на ролик/метаданными и безопасным получением credentials либо реализовать их resolver.
- **Нет уверенного восстановления зависших jobs.** Статусы могут перезаписываться запоздавшими событиями; нет версии события или защиты финальных состояний: [HandleStatus](F:/terex/main-be/internal/service/jobs/jobs.go:239). Кнопка Start для оставшегося `pending` меняет статус на `ready`, но `Update` не вызывает dispatch. Нужны отдельная команда retry/start и явные допустимые переходы состояния.
- **Неполная валидация вариантов.** Добавление пустого баннера может оставить выбранные базовые аккаунты в проверке FE, хотя backend их уже не использует: [canUploadAll](F:/terex/FE/src/app/admin/upload-video/page.tsx:96), [Create](F:/terex/main-be/internal/service/jobs/jobs.go:128). Задача создается без получателей. Изменения аккаунтов по имени также неоднозначны для одинаковых имен разных платформ: [jobs.go](F:/terex/main-be/internal/service/jobs/jobs.go:192). Нужны account IDs и проверка реально используемого плана.
- **`full` не гарантирует полный охват видео.** [GroupSegments](F:/terex/gpu-be/internal/service/candidate/subtitles.go:84) строит интервалы по распознанной речи: начало до первого сегмента и хвост после последнего исключаются. Без речи возможен успешный `done` с нулем клипов. Следует решить продуктовый контракт: полное покрытие длительности видео либо явно названная нарезка речевых сегментов; нулевой результат должен быть понятным отдельным исходом.
- **Retry не покрывает некорректный JSON внутри ответа модели.** В [llm.Find](F:/terex/gpu-be/internal/repository/llm/llm.go:301) ошибка `ParsePicks` сразу прекращает обработку. Повторы транспортных/внешних JSON-ошибок не решают этот сценарий. Нужен ограниченный повтор генерации/repair для содержимого ответа, валидация схемы и сохранение уже полученных результатов частей.
- **Совместимость media runtime требует проверки.** Команда PNG/JPG-баннера использует `scale2ref` с `ref_w/ref_h`: [ffmpeg.go](F:/terex/gpu-be/internal/repository/ffmpeg/ffmpeg.go:121). В [официальном исходнике FFmpeg 4.4](https://raw.githubusercontent.com/FFmpeg/FFmpeg/n4.4/libavfilter/vf_scale.c) таких переменных нет; эта ветка соответствует обычному ffmpeg в Ubuntu 22.04, на которой основан Dockerfile.base. Образ registry `latest` не проверен, поэтому это риск совместимости исходного Dockerfile, а не результат запуска production-образа. Нужны закрепленная версия и smoke-тест фильтров. Для видео-баннера также следует явно выбирать аудио исходника через `-map 0:a?`: сейчас действует [автоматический выбор потоков FFmpeg](https://ffmpeg.org/ffmpeg.html#Automatic-stream-selection), способный предпочесть звук баннера с большим числом каналов.
- **Локальный запуск и production-сборка недостаточно воспроизводимы.** Compose передает `RUNTIME_BASE`, но [gpu-be/Dockerfile](F:/terex/gpu-be/Dockerfile:17) всегда берет частный base-образ `latest`. Обещанный переключатель CPU/GPU не применяется этим Dockerfile. CI строит и выкатывает master без отдельного запуска unit/contract тестов и без `rollout status`: [workflow](F:/terex/.github/workflows/build-and-deploy.yml:129). Нужны pin образов, явный local CPU base, проверки PR и проверяемое завершение rollout. Открытые порты и anonymous Admin Grafana в local compose следует ограничить localhost или доверенной сетью при использовании на доступном извне хосте.

**Где можно снизить стоимость обработки**

В [renderer](F:/terex/gpu-be/internal/service/renderer/renderer.go:57) сначала обрабатывается целое видео, затем создаются баннерные варианты и лишь после этого вырезаются короткие клипы. Каждый отдельный шаг может снова кодировать видео. Для highlights приоритетно измерить подход «вырезать выбранные интервалы → сдвинуть timestamps субтитров → применить общий filtergraph → один финальный encode». Процент экономии без benchmark утверждать нельзя.

Кроме того, preproc создает 480p video proxy, который текущие candidate/renderer не читают: [preproc.go](F:/terex/gpu-be/internal/service/preproc/preproc.go:55). Его следует использовать для визуального анализа/preview либо убрать лишнее создание. Whisper запускается отдельной командой для каждого видео; стоит сравнить текущий CLI с постоянным STT-worker, который держит модель в памяти. Транскрипт и ответы LLM-частей нужно сохранять до следующего дорогого шага. Для MinIO нужны сроки хранения промежуточных данных, уборка сирот после сбоев и понятное удаление результатов job.
