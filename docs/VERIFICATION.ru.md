# Проверка процесса публикаций

Проверка выполнена 3 октября 2026 года в ветке `codex/youtube-publishing`.
Реализованный код находится в `F:\terex`. Изменения не развёрнуты на рабочем сервере.

## Выполненные проверки

| Проверка | Результат |
|---|---|
| Go tests: `proto`, `main-be`, `gpu-be` | Прошли |
| PostgreSQL 16: миграции и 15 интеграционных сценариев | Прошли на отдельной тестовой БД; каждый тест создаёт собственную schema |
| HTTP: конфликт версии и неверные данные | Проверены ответы 409 и 400 |
| RabbitMQ: persistent commands и publisher confirms | Прошли на отдельном тестовом broker до сбоя Docker Desktop |
| Frontend: 10 tests | Прошли |
| Frontend: TypeScript и production build | Прошли; собраны 15 маршрутов |
| FFmpeg media smoke | Прошёл на Ubuntu 22.04 / FFmpeg 4.4.2 с пакетами runtime |
| Календарь и редактор в браузере | Проверены на локальном mock API с созданным тестовым proxy-видео |
| Google Cloud и локальная OAuth-конфигурация | Созданы отдельный проект, consent screen и Web client; API включён, callbacks и Compose environment проверены |
| Полный цикл на реальном YouTube-канале | Не выполнен: требуется запуск локального стека и подключение тестового канала |
| Production GPU image | Не проверен: registry base image возвращал HTTP 503; Docker Desktop не запускался |

PostgreSQL tests проверяют карантин старых публикаций, удаление фиктивного `stub-*` ID из
активного результата, ручное подтверждение старого плана, независимые расписания и перенос
одного аккаунта, неизменный относительный anchor, повторное одобрение после сохранения,
защиту ручных версий от auto-approve, дубли команд, истечение lease, старый ответ worker,
отмену перед выпуском, поздний render, лимит пяти ошибок с backoff и сброс лимита при ручном
повторе, неподдерживаемый provider, неготовый asset, историю checkpoints, закрепление видимости,
OAuth state с однократным использованием, сохранение channel binding и credential reference
при ошибке, подтверждение правильного канала, reconnect и редактирование получателей уже
поставленной в очередь задачи.

HTTP YouTube tests проверяют private resumable upload, серверную позицию после разрыва,
checkpoint перед передачей последних байтов, восстановление потерянного финального ответа,
неопределённый результат истёкшей session, отсутствие повторного insert, отдельную проверку
processing, изменение видимости с сохранением остальных writable status fields и readback.
Выбор public/unlisted/private и отображение hashtags также покрыты тестами. Общий worker
проверен с provider, который получает файл по URL и не реализует отдельный выпуск.

Media smoke выполняет настоящий FFmpeg: создание видео со звуком → обрезка → вертикальный
1080p render → ASS subtitles → PNG banner; отдельно проверяется video banner и сохранение
исходной звуковой дорожки. Из-за отказа Docker запуск использовал изолированный Linux chroot
с официальным Ubuntu Base и теми же пакетами `ffmpeg` / `fonts-liberation`; это проверка
медиакоманд, а не сборки полного production image с CUDA, Whisper и Torch.

В браузере проверены UTC ↔ Asia/Tomsk, перенос одного события, недельный и месячный
календарь, открытие редактора с настоящим тестовым proxy-видео, изменение границ,
заголовка, видимости и текста cues. Сохранение создало новую версию и перевело будущие
публикации в `on_hold`; подтверждение одобрения внутри страницы вернуло обе публикации
в `scheduled`. Отмена одной публикации через отдельное подтверждение оставила вторую
в расписании. Редактор проверен на ширине 390 px: мобильная навигация доступна,
горизонтального переполнения нет. Браузерные проверки используют локальный mock API;
переходы настоящего хранилища отдельно проверены PostgreSQL tests.

## До запуска

1. Google Cloud настроен в отдельном проекте **Terex Local** (`terex-local-510513`):
   YouTube Data API v3 включён, приложение в режиме External / Testing, scope
   `https://www.googleapis.com/auth/youtube.force-ssl`, тестовый пользователь
   `terex123321@gmail.com`. Web client **Terex Local** содержит callbacks
   `http://localhost:3000/api/accounts/oauth/callback` и
   `https://terex.legendary-trio.me/api/accounts/oauth/callback`;
   `legendary-trio.me` зарегистрирован в authorized domains. Client ID и secret
   импортированы из Google JSON в локальный `F:\terex\.env`, который игнорируется Git.
   Docker Compose проверен без вывода значений credentials: они передаются только `gpu-be`,
   оба backend получают одинаковый локальный callback. Домен зарезервирован в OAuth;
   DNS, HTTPS и развёртывание на нём пока не выполнялись. Локальный стек сейчас не запущен;
   подключение канала и полный OAuth callback требуют его запуска по [инструкции](PUBLISHING.ru.md).
   Secret передаётся только `gpu-be`; actual credentials и refresh token хранятся в
   закрытом служебном bucket. Не запускать второй OAuth gateway с общими credentials:
   текущая сериализация refresh действует в одном процессе. Для нескольких gateway
   потребуется распределённая блокировка CredentialStore.
2. Восстановить Docker Desktop и доступ к production GPU base image. Выполнить media smoke
   в самом production image и собрать/запустить весь stack. В CI уже добавлена проверка
   отдельного CPU image с runtime media packages.
3. Подключить тестовый YouTube-канал и подтвердить его channel ID. Проверить private upload,
   обработку, выбранную видимость и внешнюю ссылку; затем restart посреди upload, reconnect,
   независимые расписания двух аккаунтов и отмену до выпуска. Для public/unlisted проверить
   отсутствие ограничений Google API project.
4. Просмотреть старый backlog в календаре и вручную подтвердить нужные планы. Старая очередь
   и stub больше не могут подтверждать успех нового процесса.

Тестовые команды и подготовка окружения описаны в [PUBLISHING.ru.md](PUBLISHING.ru.md).
Не использовать рабочую PostgreSQL или рабочий канал для разрушительных сценариев тестов.

При настройке один раз в диагностический вывод попала строка созданного client secret.
Перед production-запуском замените этот secret в Google Cloud и повторите локальный импорт
JSON нового секрета. Само значение в этот отчёт не включено.
