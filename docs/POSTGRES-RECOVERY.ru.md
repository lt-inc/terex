# PostgreSQL: запуск, восстановление и диагностика

`main-be` и `twitch-collector` ожидают доступность PostgreSQL при запуске.
Повторяется только проверка подключения, с задержкой от 100 мс до 2 секунд.
Миграции и бизнес-транзакции автоматически не повторяются: неизвестный результат
SQL нельзя безопасно считать неуспешным и выполнять снова.

## Настройки

`DB_STARTUP_TIMEOUT` ограничивает суммарное время подключения и миграций:
по умолчанию `60s` для `main-be`, `30s` для `twitch-collector`. Значение задаётся
в формате Go duration, например `90s`; неверное или неположительное значение
останавливает запуск с ошибкой конфигурации. Завершение приложения прерывает
ожидание. После исчерпания срока приложение завершается с ошибкой.

Общий helper `proto/pgxutil` задаёт небольшие пулы: максимум 4 подключения,
минимум 0, период фоновой проверки 30 секунд. Положительный `connect_timeout`
из DSN сохраняется; иначе используется 5 секунд. Параметры `pool_max_conns`,
`pool_min_conns`, `pool_min_idle_conns`, `pool_health_check_period` и другие
параметры пула можно явно задать в `DATABASE_URL`. Минимум не должен превышать
максимум. Параметры пула удаляются из конфигурации соединения для миграций,
чтобы PostgreSQL не получил неизвестные настройки `pool_*`.

Временные сетевые ошибки и отказ подключения во время остановки/восстановления
БД допускают повторную проверку до срока запуска. Неверный пароль, отсутствующая
БД, ошибки конфигурации и сертификатов не скрываются ожиданием. TLS-настройки
DSN сохраняются. После запуска обычный pgxpool заменяет потерянные соединения;
перезапуск всего пула и повтор уже выполнявшихся операций не добавлены.

## Отмена рендера при недоступности coordinator

Рендер немедленно останавливается, если coordinator не подтвердил продление
lease. Ошибка RPC теперь сохраняется в причине отмены и возвращается обработчику
очереди, поэтому trace показывает ошибку вместо успешного завершения. Отказ
в lease и штатное завершение приложения сохраняют прежнее поведение.
Если сообщение об ошибке рендера также не удалось записать через coordinator,
возвращаются обе причины. Успешно сохранённая терминальная ошибка подтверждается
очереди, как и раньше.

## Что установлено по инциденту 6 октября 2026

В предоставленном trace соединения с PostgreSQL успешны около 23:24 по Томску,
затем подключения coordinator получают `connection refused` около 23:27.
В предоставленном логе PostgreSQL запускается в 23:30:09 после остановки
в 23:30:02. Эти данные подтверждают недоступность БД и отдельный перезапуск,
но не устанавливают причину остановок.

`server refused TLS connection` при `sslmode=prefer` может сопровождать
попытку TLS перед обычным подключением. Следующий `57P03: database system
is shutting down` описывает остановку сервера. Отключение TLS не устраняет её.
`ffmpeg: signal: killed` также не доказывает OOM: процесс завершается при отмене
его execution context, в том числе после ошибки продления lease.

В `lt-inc/k3s` проверки PostgreSQL раньше использовали `pg_isready` и для
готовности, и для перезапуска с таймаутом Kubernetes по умолчанию в 1 секунду.
Это создаёт риск повторных остановок при нагрузке или медленном восстановлении.
Сопутствующее изменение разделяет startup/readiness и проверку живого процесса.
Сведения о причинах перезапуска, событиях, OOM и фактическом размещении собираются
по runbook `docs/postgres-probes.md` в репозитории k3s. Увеличивать лимит памяти
без проверки вместимости узла и пикового потребления не следует.

## Проверка изменений

Unit tests проверяют настройки DSN, классификацию ошибок, дедлайн, отмену
ожидания и сохранение причин отмены рендера. Интеграционные проверки миграций
используют отдельную PostgreSQL и изолированные schema:

```sh
go test ./proto/... ./gpu-be/...
TEST_DATABASE_URL="$DISPOSABLE_MAIN_DATABASE_URL" \
  go test ./main-be/internal/repository/postgres -run 'TestMigrateContextWithPoolParameters|TestCanceledStartupDoesNotRunMigrations' -v
COLLECTOR_TEST_DATABASE_URL="$DISPOSABLE_COLLECTOR_DATABASE_URL" \
  go test ./twitch-collector/internal/repository/postgres -v
go vet ./proto/... ./main-be/... ./gpu-be/... ./twitch-collector/...
```

Collector integration tests удаляют свою schema; указывайте только одноразовую
БД с именем, заканчивающимся на `_test`. Не используйте рабочие credentials.

При первом прогоне main-be выявлен существующий сбой
`TestTwitchFlowsScheduleAtomicallyAndKeepEditedCompilationsManual`, также
воспроизведённый на неизменённом `origin/master` `62cec92`. Причина — разные
часы фикстуры и БД: тест использует 08:00/09:00 UTC, а `next_attempt_at`
получает реальные часы PostgreSQL через `DEFAULT now()`. После 09:00 публикации
не проходят условие готовности. Фикстура теперь явно приводит `next_attempt_at`
к тестовому времени, как соседний integration test. Полный прогон main-be и
collector, включая PostgreSQL integration, проходит без исключения тестов.
Изменение касается теста; логика расписаний сервиса не менялась.

6 октября 2026 локальная PostgreSQL 16.3 на отдельном порту использовалась для
проверок миграций и восстановления. При реальной остановке БД активное соединение
возвращало ошибку; после запуска тот же пул снова выполнял `SELECT 1`.
Отдельно проверен запуск нового пула при изначально недоступной БД с последующим
восстановлением сервера. В обоих случаях доступность восстанавливалась после
пяти проверок примерно за 1,6 секунды. Несуществующая БД завершала ожидание
после первой проверки. Проверка не перезапускала рабочую PostgreSQL 17.

Рабочий кластер не изменялся. Причину наблюдавшихся перезапусков необходимо
подтвердить previous logs и событиями именно LT-Inc k3s. Локальная проверка
восстановления не измеряет ресурсы и скорость восстановления staging.
