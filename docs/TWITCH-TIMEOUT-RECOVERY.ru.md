# Таймауты Twitch: исправления и проверка на стейдже

## Что меняется

- Внутри прежнего общего лимита соединений main-be одно соединение резервируется для коротких управляющих операций: collector-config, pressure, render Renew и чтения reset-состояния. При стандартном лимите четыре это три основных и одно управляющее соединение; общее количество не увеличивается.
- Collector-config читается одним согласованным read-only snapshot. Устаревшая конфигурация по-прежнему не разрешает новые скачивания после 30 секунд без успешного обновления.
- Admissions использует отдельные выборки для категории и каналов. Индекс исключённых источников избегает полного просмотра каталога для чтения блокировок.
- Наблюдения передаются пачками по 20 клипов, с пакетным чтением данных роста. Каждая пачка проверяет epoch и версию потока; повтор не создаёт новый физический импорт.
- Очереди и активные операции обновляются каждую минуту. Полная диагностика обрабатывает по два потока за минутный цикл в порядке ID, продолжая со следующего потока. Для 12 потоков полный обход занимает примерно шесть минут, если запросы проходят успешно.
- Неопрошенные потоки сохраняют прежнее время расчёта. Плановое ограничение количества потоков не создаёт ERROR; настоящий таймаут остаётся ошибкой и состоянием неполных данных. Ручное открытие диагностики по-прежнему запускает свежий расчёт конкретного потока.
- Синхронизация неактивного reset с выключенным GPU повторяется с задержками 15/30/60 секунд, с предупреждением при отключении и сообщением о восстановлении. Активный reset сохраняет обязательное подтверждение остановки обработчиков. GPU после перезапуска не открывает обработчики до получения актуальной epoch.
- HTTP-сбой имеет одну основную запись с причиной и trace. Повторяющийся YouTube RSS 404 получает задержку 5/15/60 минут и статус канала в панели, без удаления канала.

## Настройки и Grafana

Настройки стейджа и дашборд находятся в связанном PR репозитория k3s. Новые секреты, увеличение CPU/RAM и дополнительные исполнители не требуются.

| Переменная | Значение | Назначение |
|---|---:|---|
| `DB_CONTROL_POOL_RESERVED_CONNS` | `1` | Резерв внутри существующего общего лимита; `0` отключает разделение. При общем лимите один резерв отключается с предупреждением |
| `TWITCH_MONITOR_FLOWS_PER_TICK` | `2` | Максимум полных диагностик за минутный цикл; положительное целое число |

На стейдже значения задекларированы в ConfigMap `terex-be-config`. Применение ConfigMap требует перезапуска Deployment `terex-be`, чтобы обновились переменные среды. Изменения Terraform выполнять без одновременного CI-деплоя.

В Grafana общие очереди считаются устаревшими после **180 секунд**, а полная диагностика отдельного потока — после **600 секунд**. Таблицы показывают возраст расчёта и фактическое время чтения collector. Отчёты поиска читаются из сохранённого снимка каждого потока: обновление двух потоков не убирает данные остальных десяти. Старые снимки не получают новую дату от обновления общих очередей. После десяти минут их числовые значения не показываются как свежие.

В системном снимке сохраняются `flows_total`, `flows_per_tick`, `flows_attempted`, `main_flows_observed` и `next_flow_id`. Нулевые или отсутствующие сведения скачиваний при недоступном collector не интерпретируются как пустая очередь.

## Базовая выборка и проверка после выкладки

До выкладки получены следующие показатели аудита 12 октября 2026 года. Это отдельная часовая выборка, а не результат новых изменений.

| Показатель | До изменений | После выкладки |
|---|---:|---|
| Неуспешные collector-config / все запросы | 24 / 708 | Заполнить по сопоставимому часу |
| Неуспешные pressure / все запросы | 10 / 259 | Заполнить по сопоставимому часу |
| Успешные admissions / все запросы | 50 / 50 | Проверить также задержки, HTTP 200 не означает быстрый расчёт |
| Пример медленного admissions | 14,79 с всего; 13,85 с расчёт, из них 9,91 с — выборка 87 кандидатов | Сопоставить этапы при неизменных потоках и квотах |
| Примеры ожидания соединения | Config — 8 с; pressure — 4,97 с без выполненного SQL | Должны перестать зависеть от занятого основного пула |
| Полные циклы диагностики прежнего алгоритма | 32 из 59 циклов полностью опросили 12 потоков | Считать успешность двух назначенных потоков и возраст всех 12, а не требовать полный обход за минуту |
| CPU steal VPS | Около 66% за пятиминутный замер | Отмечать отдельно от SQL и ожиданий соединения |

Порядок выкладки:

1. Выпустить совместимые изменения main-be и collector, включая аддитивный индекс. Сохранить потоки, квоты, epoch, импорты и файлы; сброс Twitch не нужен.
2. Применить настройки и дашборд k3s, затем обновить main-be. Использовать только явно выбранный kubeconfig LT-Inc.
3. Наблюдать 30–60 минут: config/pressure, admissions, время Observe, ожидание пулов и render Renew. Зафиксировать количество запросов, а не только ERROR-строки.
4. Проверить работу в течение суток: все потоки получают очередную диагностику, её возраст обычно меньше десяти минут, новые скачивания идут только при свежей конфигурации, не появляются дубли и новые нарушения квот.

Критические проверки: идемпотентный повтор пачки Observe и сохранение версии/epoch; разделение пула без увеличения общего лимита; round-robin диагностики без обновления времени неопрошенных потоков; восстановление GPU с закрытым gate до синхронизации; активный reset не продолжает удаление без drain-подтверждения.

Локально на изолированной PostgreSQL 16 сравнили старую и новую выборку admissions на синтетическом каталоге из **30 000 кандидатов**, принудительно используя generic prepared plans. Во всех **24 сочетаниях** категории/каналов/legacy, языка без фильтра/ru, исчерпанной/доступной квоты и наличия/отсутствия нового спроса совпали идентификаторы и порядок результатов, включая приоритет восстановления.

| Синтетическая выборка категории с языком ru | Старый запрос | Новый запрос |
|---|---:|---:|
| Время исполнения в сохранённом прогоне | 88,93 мс | 4,02 мс |
| Обращения к буферам PostgreSQL (`shared hits`) | 2 314 | 514 |
| Использован индекс категории/языка | Нет | `twitch_imports_admission_category` |

Это проверка плана запроса на локальных искусственных данных, **не замер производительности стейджа** и не обещание такого же ускорения полного admissions. Предыдущий отдельный прогон дал 95,83/2,39 мс; малую выборку не использовать для p95. Сохранены helper, журнал и оба JSON EXPLAIN в `F:/terex-audit-tools/candidate-generic-*`; проверка выполнялась временным Go overlay без дополнительного постоянного теста.

Существующая проверка роста также покрывает вычисление аномалии относительно десяти измерений из той же пачки и повтор пачки без изменения `xmin` импортов и конфигурации источников. Поле последней проверки и другие поля отображения больше не попадают в конфигурационный snapshot каждого исходника: иначе они приводили к массовому UPDATE даже при неизменной версии настроек.

Дашбордовые SELECT проверяются read-only по действующим снимкам стейджа; это проверка совместимости SQL, **не** подтверждение ускорения после выкладки. Малую выборку задержек не считать надёжным p95. Если CPU steal остаётся высоким, нужен перенос VPS на менее перегруженный хост.

Для отключения резерва установить `DB_CONTROL_POOL_RESERVED_CONNS=0` и перезапустить main-be. Число диагностик управляется независимо; возвращать прежний массовый обход при перегруженной БД не рекомендуется. Индекс и поля снимков аддитивны и не требуют удаления данных при откате приложения.
