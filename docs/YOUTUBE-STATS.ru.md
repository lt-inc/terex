# Статистика YouTube-аккаунтов и дашборд

`stats-collector` раз в час читает статистику каналов, подключённых в Terex
(таблица `accounts`, `platform='youtube'`, `connection_state='connected'`), и пишет снапшоты
в схему `yt_stats` БД `main`. Grafana-дашборд **Terex YouTube Stats** (папка *Terex*,
uid `terex-youtube-stats`) читает эти таблицы напрямую через datasource `postgres-main-ds`.

Сборщик не видит токенов и не ходит в YouTube сам. Он вызывает gRPC `Gateway/ChannelStats` в `gpu-be`
(тот же порт `:9090`, что у `GpuService`): `gpu-be` берёт токен аккаунта из bucket `credentials`
(при необходимости обновляет его, как при публикации), читает `channels.list?mine=true`, последние
загрузки и `videos.list` и возвращает готовые счётчики. Запросы идут от имени владельца канала,
поэтому видны приватные и unlisted видео. Статусы ответа: `ok`, `needs_reauth` (аккаунт ждёт
переподключения, пропускается, история остаётся), `quota` (проход прерывается), `error`.
Watch time, retention, трафик и демография требуют YouTube Analytics API и scope
`yt-analytics.readonly` (переподключение аккаунтов) — пока не реализованы.

## Как добавляется канал

Никак вручную. Подключите YouTube-аккаунт в админке Terex (OAuth) — после ближайшего прохода
сборщика (до `STATS_INTERVAL`) канал появится в переменной **Канал** и получит свой ряд панелей.
Дашборд не редактируется и Terraform не применяется. Удалённый аккаунт исчезает вместе с историей
(`DropRemoved`). Чтобы не ждать час, перезапустите Deployment:
`kubectl rollout restart deployment/terex-stats-collector -n admin`.

## Дашборд

- Сверху: число каналов, подписчики, просмотры (всего и за период), число видео, «Последний успешный сбор»
  (красный — сборщик стоит).
- **Топ каналов по просмотрам** (bar gauge) и таблица каналов: подписчики, прирост за период, просмотры,
  прирост просмотров, видео, среднее на видео.
- Прирост просмотров по дням и динамика подписчиков по каналам.
- Топ видео по просмотрам и по приросту за период (просмотры, лайки, комменты, ER %, длительность);
  название — ссылка на YouTube. Размер топа — переменная **Топ видео**.
- Свёрнутая строка **Сборщик статистики** — история проходов и израсходованная квота.
- Строка **Канал: …** повторяется для каждого выбранного канала: подписчики, просмотры, ER,
  графики, топ видео и последние публикации.

«За период» считается по снапшотам: значение на конец интервала минус значение на его начало
(если истории до начала нет — минус самый ранний снапшот, т.е. период короче запрошенного).
Скрытый владельцем счётчик подписчиков хранится как `NULL` и в сумму не входит.
ER = (лайки + комментарии) / просмотры по отслеживаемым видео.

## Конфигурация

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `DATABASE_URL` | — | БД `main` (то же, что у `terex-be`); сервис читает `public.accounts`, пишет в `yt_stats` |
| `GPU_GRPC_ADDR` | `gpu-be:9090` | gRPC `gpu-be` (в k3s `terex-gpu-be.admin.svc:9090`) |
| `STATS_INTERVAL` | `1h` | период прохода (минимум `1m`) |
| `MAX_VIDEOS_PER_CHANNEL` | `200` | сколько последних загрузок канала отслеживать |
| `FULL_RESOLUTION_DAYS` | `14` | сколько дней хранить все снапшоты; старше — по одному на сутки |
| `HTTP_ADDR` | `:8080` | `GET /health` (503, если нет успешного прохода дольше 3 интервалов) |

Квота общая для Google-проекта (тот же, что у публикации): каждый `list`-запрос стоит 1 юнит. Проход ≈ 8 юнитов на канал (200 видео), при часовом
интервале ≈ 200 юнитов в сутки на канал при лимите 10 000 в сутки на проект.
При `quotaExceeded` проход прерывается, ошибка видна в «Запуски сборщика» и в индикаторе последнего сбора.

## Выкладка (staging)

1. Новые секреты не нужны: используются уже подключённые аккаунты и `GOOGLE_CLIENT_ID/SECRET` в `gpu-be`.
   Выкатывать нужно и `terex-gpu-be` (новый метод `ChannelStats`), и `terex-stats-collector`;
   сначала `gpu-be`, иначе сборщик получит `Unimplemented` и проход завершится ошибкой.
2. k3s: `terraform apply` создаст Deployment `terex-stats-collector`, ConfigMap, `InfisicalSecret`
   и обновит ConfigMap дашбордов (`k3s/admin/terex-stats-collector*.yaml`,
   `k3s/monitoring/dashboards/terex/terex-youtube-stats.json`).
3. Terex CI собирает образ `terex-stats-collector` и обновляет image существующего Deployment
   (шаг не валит релиз, пока Deployment ещё не создан Terraform'ом).
4. Проверка: логи `stats pass done channels=N`, `GET /health`, дашборд в папке *Terex*.

Схема создаётся сервисом при старте (`CREATE SCHEMA IF NOT EXISTS yt_stats`), поэтому роль из
`TEREX_DATABASE_URL` должна иметь `CREATE` на БД `main`. Если нет — один раз выполните
`CREATE SCHEMA yt_stats AUTHORIZATION <роль>`.

## Разработка

`cd stats-collector && go test ./...`; логика запросов к YouTube тестируется в `gpu-be` (`repository/youtube`, `service/workflowgateway`). Тесты `internal/store` и `internal/service` требуют одноразовую БД:
`STATS_TEST_DATABASE_URL=postgres://… go test -p 1 ./...` (он пересоздаёт схему `yt_stats`
и таблицу `public.accounts`, если её нет — не указывайте рабочую БД).
